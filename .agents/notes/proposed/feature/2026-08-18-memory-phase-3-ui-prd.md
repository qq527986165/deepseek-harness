# Agent Note: Memory Phase 3 UI — PRD and decision record

Status: proposed

English | [中文](2026-08-18-memory-phase-3-ui-prd.zh.md)

## Problem

Phase 2 shipped the automatic mechanism — session-start injection, every-turn distillation with scope classification, journal appends, the `memory/inject` and `memory/distill` session events, and the guidance section — but users see memory only through Obsidian, the `memory_read`/`memory_search` tool results, and the session log. The proposal reserves Phase 3 as the first user-visible surface, and the design discussion for it needs a living record: the frozen scope, the open questions to settle, and every decision as it lands, so development starts only after all open questions are decided and the implementation plan is signed off. Each discussion round appends to the decisions log and re-records the bilingual pair. The design source of truth is the [first-party memory proposal](2026-08-18-first-party-pluggable-memory.md) (`Automatic memory lifecycle`, `Phasing`, `Acceptance criteria`); the shipped Phase 2 baseline is the [automatic lifecycle note](../../implemented/feature/2026-08-18-memory-phase-2-automatic-lifecycle.md).

## Proposal

The Phase 3 window owns exactly five surfaces, from the proposal's Phasing and the original window instructions:

1. **Management panel** for both scopes — list, read, edit global and project notes.
2. **`/memory review`** promotion flow — the model proposes project→global upgrades, the user confirms.
3. **`memory_delete`** with the lifecycle policy — review, TTL, and link repair.
4. **Conversation nodes** showing distilled writes.
5. **Settings page** for the memory mechanism (config surface for users).

Nothing else enters without an explicit user request. The open questions below are the discussion agenda; each settled item moves to the decisions log.

### A. Panel shape and entry points

Decided: a `sidebar.footer.action` button opens the panel as a right-side drawer registered into `shell.overlay` — both additive list slots, so ui-layout and ui-sidebar stay untouched; there is no dedicated route (the shell has no URL routing) and no command-bar entry. The panel is one surface with scope tabs (global / project), never side-by-side with the conversation: the panel is cross-session while the conversation column is session-scoped. Each selected scope has two collection filters: Journal Memory lists every document under that vault's `journal/`, and Node Memory lists every document under `notes/`; the project scope first selects the project and then applies the same filters. Search stays inside the selected scope and collection. Node view uses `MarkdownText` for reading and a field-based edit form (title, body, tags — frontmatter stays provider-owned); journal documents are read-only. Node↔journal and predecessor links navigate inside the panel to the exact file or journal-entry anchor, backlinks show beside the read view, and dangling links keep their marks. The project tab's workspace source is settled under E. UI implementation changes remain paused until the corrected distillation commit flow is complete.

### B. UI style and copy

Decided: the repo client rules apply unchanged — Chinese product copy, CSS Modules with `--dsw-*` semantic aliases, no literal colors, no component library, no Tailwind. All panel strings ride a locale namespace on the slot registrations (`settings.memory` style key) with i18n records committed beside the package; the entry icon reuses the existing `ui-primitives` icon set. The list is a compact two-line row (title, then tags + relative updated time) at ui-settings density — no card grid in the first version. Badges: no scope badge (scope is the tab axis and search stays per-tab), tags as badges (at most 3 plus an `+N` overflow, click-to-filter), `updated` as relative-time text, and `MEMORY.md` carries a persona label.

### C. Conversation nodes

Decided: one single-event `ConversationNodeDefinition` (kind `memory-distill`) in `ui-memory`; `match` returns `{ id: String(event.seq), role: 'start' }` for a committed `memory/distill` receipt only, `start` folds the whole payload into State, there is no update path, `publication: 'immediate'`, and no `buildLocationData` (no consumer). The lifecycle appends that event only after every node, journal entry, reciprocal link, index row, and read-back check for the completed user-prompt-to-assistant-answer turn succeeds. A turn with no durable candidate or any failed/partial commit emits no event and therefore no conversation node. The keyed renderer shows one chip per committed node, including every project and global node from a mixed-scope turn; each chip opens that exact Node Memory document. It shows no journal chip and no partial-failure row: users reach the corresponding Journal Memory entry through the node's source link. Chip clicks open the panel through a registrant-private open-request source carried in the panel register's inject `hooks` compartment (bound to a `useMemoryPanelOpen()` hook), with the node's inject face exposing an `openNote(ref)` callback — a store handle cannot mount under two scopes (session node vs root panel), which the slot system rejects at load. The client consumes the event payload through a type-only `./types` export of `@deepseek-ai/dsh-memory-lifecycle`. Chat view only; the trajectory table gets no dedicated row in Phase 3.

### D. Commands

Decided: `/memory review` is a three-stage flow — the command handler runs one auxiliary model call (distillation-style, the session's routed model) that proposes project→global upgrade candidates bounded by a config cap, appends the log-only `memory/review` event `{ reviewId, candidates: [{ id, title, snippet, reason }] }`, and returns `{ kind: 'success', sourceEventSeq }` pointing at it. A second conversation node (kind `memory-review`, business id `reviewId`) renders candidate cards from `memory/review` (start) with per-candidate accept/reject and accept-all actions plus a panel-jump chip; decisions ride a Typert Remote `memoryReview.decide(sessionId, reviewId, decisions)` that validates the review against the session log, promotes accepted notes (write global + remove the project file — a move), and appends `memory/review-decided` `{ reviewId, accepted: [{ id, title, globalId }], rejected: [id] }` as the node's update. The generic approval seam is not used: it cannot render the memory-domain presentation (per-candidate panel jump). v1 takes no arguments — the source scope is always project and non-empty raw input returns an error; a global-only session returns a clear error text. The candidate cap is a config field (`maxReviewCandidates`, default 5), not a command argument; the model never controls it upward. The result lands in the conversation (the review node); the panel serves as the candidate inspector through chip clicks only.

### E. Remote surface for the browser

Decided: a new host-side package `@deepseek-ai/dsh-memory-remote` (`packages/memory/memory-remote/`) injects `memory` and carries two Typert Remote namespaces with the unary request/result convention. `memory` is session-independent — `list`, `read`, `search`, `write`, `delete` take no sessionId and address the project vault through an explicit `workspaceDir` that resolves through the service's `resolveScopes` (non-registered paths fail with `NO_PROJECT_SCOPE`); `memoryReview` is session-addressed — `decide(sessionId, reviewId, decisions)` (D). The memory service itself stays UI-free: its main consumers are tools and the lifecycle, and the remote mounts only in web compositions. Listing and reading distinguish Node Memory under `notes/` from read-only Journal Memory under `journal/`; a journal open may include the stable entry anchor carried by the committed receipt. `decide` composes existing primitives: `readInScope(project)` → `write(global)` → `delete(project)` (write first, then remove, so a failure leaves no missing note). Authorization: panel mutations execute directly with no approval seam — the console user is the authority, and the approval machinery requires a live agent turn, which panel operations must not depend on; the service-layer checks (sole provider, workspace-gated project scope, exclusive write chain) are the boundary. Panel mutations record no session event — the vault files plus index are the record, like external Obsidian edits, and watcher reconciliation feeds the UI. There is no journal write method on the browser remote. The client detects the remote's presence through the gateway's lazily installed namespace service: absent means the footer button is hidden (no trace), never an error.

### F. Deletion and lifecycle

Decided: `memory_delete` takes `{ ref, scope? }` (id or exact title, like `memory_read`) over a new `MemoryService.delete(ref, scope?, cwd?)` / provider `delete` primitive. Deletion is soft: the file moves to a sibling trash folder outside the vault — `$DSH_HOME/memory-trash/` for the global vault, `<project>/.dsh/memory-trash/` for a project vault — with a timestamped filename, and the index drops the note row plus its link rows. The trash folder lives outside the vault, so search and indexing never see it; restoring is moving the file back by hand (Obsidian or any file tool) and the watcher re-adopts it; v1 ships no restore button. Promotion's project-side removal is the exception: it deletes outright without the trash, because the content is already written to the global vault and a trash copy would be garbage. No automatic deletion in v1: `reviewAfterDays` (default 30) only marks notes whose `updated` age exceeds the threshold with a review badge in the panel. Link repair is index-only: rows pointing at the deleted note are dropped, file bodies are never rewritten, and surviving `[[wikilinks]]` become dangling on the next rebuild, rendered with the existing dangling marks. Model-initiated deletion requires user confirmation through the approval machinery (it runs in a live turn); panel deletion is the console user's own act with a plain confirm dialog. The approval integration detail is settled with G.

### G. Settings and permissions

Decided: one card (namespace `memory-lifecycle`: the lifecycle package registers the host half, `ui-memory` renders the browser half) with six knobs — `distill` toggle, `distillMode` (`concise` | `detailed`, default `concise`; the mode selects the fixed distillation instruction, both model-visible texts pinned by snapshot), `minTurnChars`, `maxInjectBytes`, `maxReviewCandidates`, `reviewAfterDays` — plus a read-only global vault directory display fed by a new `memory.info()` remote method. Card changes apply live: the settings write validates first, and the lifecycle re-reads its resolved config per use. `maxDistillTokens` (default raised to 2048, a hidden circuit breaker), `distillTimeoutMs`, and the auxiliary `provider`/`model` route stay plugin config — deployment knowledge, not knobs. A user-authored distillation prompt is deferred. `recentNoteCount` is removed: session-start injection becomes the two persona notes in full plus a note catalog (newest first: title, tags, updated, first-line excerpt) byte-capped by `maxInjectBytes`, with detail fetched on demand through `memory_read`/`memory_search`; this revises the Phase 2 injection mechanism, so the Phase 2 note, the first-party proposal, the `memory/inject` event semantics, and the replay snapshots update with it. No new permission preset: panel operations are the console user's own acts (E), and `memory_delete` asks through the existing `ctx.approval.request` (`toolName: 'memory_delete'`), inheriting the session's approval policy — `ask` shows the confirm card, `never` auto-rejects. No finer per-scope visibility: what the console user sees is what the host can reach (workspace-gated project scope, always-visible global scope).

### H. Composition and defaults

Decided: the `ui-memory` client package joins the web-app bundle by default and hides itself when the memory remote is absent, so users never manage the browser half; the five host packages (memory family plus `memory-remote`) stay explicitly mounted and do nothing until composed. Degradation ladder: no memory rows → no trace (no button, no node matches, no card); memory rows without `memory-remote` → same, Phase 2 keeps working without a GUI; `memory-remote` without a registered provider → the button shows and the panel renders a friendly "provider not mounted" banner; everything composed → full panel. Distribution intent, recorded for after internal functional testing: the family ships as an external-plugin-style installable bundle — a first-party `@deepseek-ai/dsh-memory-bundle` declaring `dsh.bundle` with a patch composing the five rows, published to npm, so `dsh plugin --profile <name> add @deepseek-ai/dsh-memory-bundle` installs and activates everything exactly as docs/user/develop/basic/publish.md describes. The bundle package, its installation tests, and the public release belong to a later packaging task after the feature window; users can still compose the five rows by hand until then. The code stays in this repository (open-source extraction remains out of scope), and the external distribution shape is designed now so the future move changes nothing user-visible.

### I. Verification

Decided: every model- or user-visible behavior is pinned by a keyless test, and every touched package stays inside the per-file coverage gate. Distillation coverage proves both branches: no durable candidates leave both vaults and the session log unchanged; a remembered turn writes non-empty uniquely named nodes plus scope-local journal entries with reciprocal exact-entry links, verifies the index and read paths, and only then appends a replayable `memory/distill` receipt. Failure injection at every file/index/verification step proves whole-turn rollback or recovery, including mixed project/global turns. A later same-kind memory creates a new predecessor-linked node without changing the old file, and local-calendar tests cover the configured timezone around UTC day boundaries. The replay-driven web test rebuilds the node from committed receipts alone and shows one node chip per committed ref, with no journal chip or partial-failure node. The review and deletion assembled tests remain as decided; the panel projection, settings card, and every later visible change get keyless web snapshots (`DSH_SNAPSHOT=replay pnpm run test:web`). Per-file 100% coverage covers all new and touched packages. Gates run with each change: `test:gui`, typecheck, lint, doc-sync, bilingual pair re-records, package READMEs with Model Experience sections, and generated catalogs. The Phase 2 lifecycle correction updates its implemented note, the first-party proposal, event semantics, prompts, READMEs, and replay snapshots in the same change.

## Alternatives considered

- **A generic in-dsh file viewer instead of a dedicated memory panel.** Rejected as the sole surface: the panel must know scope ownership, note identity, and the later promotion/deletion flows, which a generic viewer cannot express. A generic viewer remains a separate plugin decision and is not a Phase 3 dependency; the panel's read/edit view may reuse shared markdown primitives.
- **Obsidian only, no GUI surface.** Rejected: visibility of what was silently distilled and the `/memory review` promotion flow are user-facing promises of the proposal; without a panel they stay invisible outside the vault folders.
- **Config through cordis.yml only, no settings card.** Rejected: deployment-level config already exists, but the window instructions reserve a settings page; a settings card is the repo-standard way to give users the same knobs without editing patch files.

## Acceptance criteria

- The panel lists both scopes, opens a note, and edits persist through the provider's watcher reconciliation.
- `/memory review` shows candidates and a user confirmation promotes a note to the global vault.
- `memory_delete` removes a note with index and link cleanup.
- A conversation node rebuilds from a committed `memory/distill` receipt alone, exposes every real node and no journal shortcut, and never appears for an empty or failed pass.
- Each selected scope lists Journal Memory from `journal/` and Node Memory from `notes/`; reciprocal links navigate between an exact journal entry and its nodes.
- A remembered turn commits new nodes, scope-local journal entries, index rows, and reciprocal links atomically across project/global groups; no-memory turns write nothing, later same-kind facts create predecessor-linked nodes, and local dates follow the configured timezone.
- The settings card changes the deployment-level config fields.
- Repository gates pass: per-file coverage, keyless snapshots, bilingual docs.

## Risks

- **Remote surface widening.** Exposing memory list/write/delete to the browser is the panel's largest new attack surface; the authorization design for session-independent mutations is the riskiest piece and settles first.
- **Deletion irreversibility.** Physical deletes have no recycle bin, and a TTL could destroy user-edited notes if the policy is careless; soft delete or review-first defaults bound the damage.
- **Concurrent edits.** The panel, Obsidian, and distillation can write the same note; the provider guarantees last-write-wins at file level, so the panel must re-read before save and surface the updated timestamp to avoid clobbering.
- **Model-side deletion authority.** A silent `memory_delete` could remove user-edited notes; the authorization model decides whether deletion needs user confirmation.
- **Interrupted multi-vault commit.** A process crash can land between node, journal, and index writes across project and global vaults; staging plus recovery metadata must finish or roll back the whole turn before any success event becomes visible.
- **Append-only repetition.** New nodes preserve chronology and avoid rewriting old memories, but related facts can accumulate; predecessor links and later node-oriented views provide continuity without weakening the no-merge rule.

## Deferred

- **Intent-driven recall at request time.** Infer the user's current intent from the prompt, expand it into query terms, and inject matching memory. Recorded for evaluation together with Phase 4 semantic retrieval (the proposal reserves that decision for Phase 4: "Decided then, not now"). Costs named now: an inference call on the request critical path (visible latency) or a weak keyword extraction, prefix-cache invalidation from per-request injection, and a new injection event family with its own bounds and snapshots. Phase 3 uses catalog injection plus the model's own `memory_search`/`memory_read` on demand instead.
- **Configurable global memory vault directory.** The owner wants the global vault path configurable to an explicit absolute directory because `$DSH_HOME` may live on a space-constrained system drive. This stays deferred until the migration behavior, live reload timing, validation, and watcher ownership are designed.
- **Top-level memory settings page.** The owner wants Memory beside General, Model, Plugins, and Agent Presets instead of nested inside Plugins. This stays deferred until settings navigation and slot ownership define how first-party feature pages register at that level.

## Out of scope

- Semantic retrieval (Phase 4).
- A generic in-dsh file viewer (a separate plugin decision, not a Phase 3 blocker).
- Open-sourcing or extracting the plugin (revisit after the plugin is complete).

## Implementation plan

Development starts on explicit user sign-off. Phases ①–④ ship the feature window; ⑤–⑥ follow the user's sequence (functional testing first, then packaging); ⑦ is recorded only.

### ① Host foundation (service primitives + deletion + remote surface + mechanism revision)

- `memory`: add collection-aware `list(scope, kind, cwd?)`, `delete(ref, scope?, cwd?)`, `info()` (global vault directory); `kind` distinguishes Node Memory from Journal Memory.
